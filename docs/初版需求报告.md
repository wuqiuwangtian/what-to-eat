# “吃什么”初版需求报告

版本：v0.2｜日期：2026-10-26｜状态：已补充 GitHub 同类项目调研，未开发、未实测。

## 1. 产品定位与原始要求

这是一个帮助用户摆脱“吃什么”纠结的娱乐应用，以安卓手机用户为主。它应像一个懂口味的朋友，迅速给出一个答案，让用户不必研究推荐系统或操作复杂筛选器。

原始要求完整保留如下：

- 打开 App，点一下“吃什么？”就得到回答；不满意只需点“换一个”。
- 尽可能封装复杂度，主流程不要问卷、聊天或层层筛选。
- 后台可以深入分析历史与最近的外卖记录，建立初始画像并持续更新。
- 分析不能只靠通用大模型的直觉，应参考饮食习惯与推荐相关研究。
- 首次导入和建档可以慢；日常推荐必须快。
- 分析过程默认不展示，但给好奇用户保留查询入口。
- 尽量减少 token 费用，理想情况下可使用本地小模型。
- 关键挑战：答案是否明显优于随机，以及效果、速度和成本如何取舍。

## 2. 目标用户与价值判断

主要用户是经常点外卖、对吃什么拿不定主意、又不愿花时间做选择的安卓用户。没有订单记录的人也应能立即体验，避免导入数据变成使用门槛。

核心价值是**更快遇到一个愿意吃的答案**。还原订单、画像细致程度和模型大小都是手段，不是最终目标。初版不应把项目扩展成营养管理、医疗饮食建议或外卖交易平台。

## 3. 用户流程与交互要求

| 情境 | 用户操作 | 系统行为 |
| --- | --- | --- |
| 首次打开 | 点“吃什么？” | 立即使用基础候选给出建议；历史导入可跳过 |
| 有历史数据 | 可选导入一次 | 后台建档，有进度可查；无需等待完成才能继续体验 |
| 日常使用 | 点“吃什么？” | 根据当前上下文、画像和候选集给出一个答案 |
| 不满意 | 点“换一个” | 快速展示同一会话中不同的答案，不反复追问原因 |
| 愿意采纳 | 可选点“就它了” | 记录明确反馈；不要求每次操作 |
| 好奇推荐依据 | 打开次级入口“为什么推荐” | 展示真实依据、画像摘要和数据更新时间 |
| 想修正偏好 | 进入次级设置 | 修改预算、忌口、口味，或清除画像与记录 |

主屏只保留一个突出按钮或一个答案卡片；答案出现后，“换一个”仍是主要操作。可选反馈不能成为继续使用的前置条件。

答案建议以一道菜或一个明确餐食组合为基本粒度，例如“番茄牛腩饭”。不默认展示一整页候选。若当前只能确认菜品类别，就不要生成不存在的商家、实时价格或配送承诺。

反复换选时先在合格候选中扩大多样性；候选耗尽可轻量提示“这一轮都看过啦，再换一轮”。不能为保证每次不同而违反明确忌口。连续快速点击时，仅保留最新展示状态，避免多次云端请求堆积。

## 4. 数据获取与初始画像

### 4.1 订单获取是首个外部依赖

安卓对应用私有数据有访问隔离，不能把“用户授权存储权限”理解成能直接读取其他外卖 App 的全部订单。[Android 官方存储说明](https://developer.android.com/about/versions/11/privacy/storage)

| 数据途径 | 建议定位 | 需要先验证的事项 |
| --- | --- | --- |
| 平台提供的用户授权接口或导出 | 优先调查 | 指定平台是否实际提供个人订单访问、字段、历史跨度与调用权限；当前未确认 |
| 用户主动选择的订单截图、文件或分享内容 | 初版候选 | 至少一种输入是否稳定可得；OCR 能否还原多菜品与时间；需少量校对 |
| 少量手动记录、近期吃过清单 | 无接口时的补充 | 如何保持一次性、可跳过，避免长期记账负担 |
| App 内展示、换选和采纳事件 | 持续更新来源 | 采纳是否代表真实进食；必须区分事件含义 |
| 通知等增量来源 | 后期探索 | 通常不能提供完整历史；内容完整性、权限与平台条件待查 |

不能在未验证前承诺自动同步某个外卖平台。初版建议不依赖 root 或读取其他 App 私有目录；自动下单不在本轮建议范围内。

### 4.2 数据字段与质量

- 核心订单字段：来源、来源订单标识（若有）、时间、菜品名、商家、金额、订单状态、数据置信度。
- 可派生字段：菜系、主食、主要食材、口味、烹饪方式、餐次、价格区间、距离上次食用时间。
- 地址只在需要判断餐食可获得性时使用粗粒度区域；截图中的姓名、电话、详细地址不进入推荐画像。
- 处理重复导入、退款和取消、多份同菜、套餐、多人订单和代点情况；订单金额不能直接当作单人餐费。
- 菜品别名、OCR 和标签提取需保留来源及置信度，低置信度字段不能直接升级为硬限制。
- 历史订单不等于实际吃过，更不等于喜欢；缺失的线下饮食也不能被当成不存在。

### 4.3 画像应分层

| 层次 | 示例 | 更新方式 |
| --- | --- | --- |
| 明确限制 | 用户填写的忌口、排除食材 | 用户修改优先，模型不得自行覆盖 |
| 长期偏好 | 经常选择的菜系、主食、价格区间 | 多次行为缓慢更新，保留置信度 |
| 短期状态 | 最近连续吃辣、几天未吃某类菜 | 最近行为快速更新，随时间衰减 |
| 当前情境 | 午餐/晚餐、工作日/周末、临时预算 | 本次上下文优先，可选轻量调整 |
| 探索倾向 | 喜欢重复熟悉菜，还是愿意尝新 | 从多次反馈估计，不因一次换选定性 |

“换一个”只表示此刻不采纳，可能因为刚吃过、嫌贵或单纯想看看。它是弱负反馈，不自动等于永久讨厌某类食物。

## 5. 推荐与分析思路（建议，待验证）

### 5.1 重分析与快速推荐分离

```text
首次导入 → 去重/解析/菜品归一 → 长短期画像 → 本地候选与特征缓存
新增订单/反馈 → 增量更新画像和统计 → 刷新候选缓存
点击按钮 → 过滤不可选项 → 轻量排序与受控抽样 → 展示一个答案
查询依据 → 读取本次真实决策记录 → 展示简明说明
```

首次可批量处理较长历史，但旧数据应随时间降低权重。日常只处理新增记录、画像变化和当前候选，不在每次点击时重读全部订单或重新做长推理。导入中断应可续传或重试，不破坏上一次可用画像。

候选菜品可以先来自历史记录和经过整理的基础菜品库。没有可靠商家数据时，先做好“吃什么菜”的决定；“在哪买、此刻能否送达”作为独立的数据接入问题。

### 5.2 候选过滤与排序

明确限制先过滤，再结合长期偏好、餐次匹配、预算适配、近期重复程度、探索价值和本会话已展示内容排序。可把评分写成可解释的若干项，而不是让大模型凭空给出结论。

重复既可能代表喜爱，也可能带来厌倦；两者强度应按人、菜品和时间间隔区分。可从简单衰减统计、规则或小型排序模型开始，再比较是否需要更复杂的序列模型。相关研究与适用限制见[研究与验证计划](研究与验证计划.md)。

### 5.3 AI 和本地模型的分工

| 环节 | 建议起点 | 何时值得增加模型 |
| --- | --- | --- |
| 截图解析、菜名归一、语义标签 | OCR、词典、规则与可选小模型 | 非标准菜名频繁导致规则失败时 |
| 画像构建 | 统计特征和可检查的结构化摘要 | 有足够真实反馈证明语义归纳有增益时 |
| 日常选择 | 本地过滤、排序、缓存 | 轻量排序已遇到可量化瓶颈时 |
| “为什么推荐” | 来自真实打分与记录的模板 | 用户主动需要自然语言说明时，可选生成 |

本地小模型保留为理想方向，但必须比较端侧规则、传统小模型与生成式小模型；后者并不天然更快。具体模型、运行框架和技术栈留待设备基准测试后确定。

分析查询展示“你近期较常选择米饭类”“本轮未推荐重复菜”等可核对事实，以及时间、数据范围、置信度。无需展示模型内部思维过程，也不能事后编造听起来合理的原因。

## 6. 性能、成本与数据控制

下表是建议验收起点，需选定最低支持机型、系统版本、候选规模与是否联网后修订，当前没有实测数据。

| 项目 | 建议目标 |
| --- | --- |
| App 已就绪时点击到答案 | 本地常用路径 P95 ≤ 500 ms |
| 同会话“换一个” | 有缓存时 P95 ≤ 200 ms |
| 冷启动到可操作 | 参考机型 P95 ≤ 2 s，单独统计 |
| 首次画像建立 | 可后台运行、可恢复；先按 1,000 条订单不含 OCR ≤ 5 分钟做实验门槛，截图解析单独计时 |
| 无网/模型不可用 | 继续使用缓存画像与基础菜品库，不阻断主流程 |
| 常用推荐路径的云端 token | 目标为 0；导入、更新和主动解释另计 |
| 本地资源 | 必须测内存、模型包体、耗电、发热；不能用无 API 费代替成本评估 |

云端费用按“输入 token × 输入单价 + 输出 token × 输出单价”统计，并统一单价计费单位。分别记录首次导入、每日增量、解释查询和普通换选的费用；在供应商与模型未定前不写死人民币成本。

云端处理应可关闭；使用前说明哪些数据会上传，并优先上传去标识后的结构化片段。用户可以查看、纠正、导出和删除历史与画像。删除应同时失效相关缓存；原始截图建议处理后由用户选择是否保留。这些是与订单数据直接相关的产品要求。

## 7. 如何证明比随机更好

比较必须使用相同的候选集、忌口过滤和情境条件，不能让随机基线推荐明显不可吃的选项，从而制造优势。

| 对照方案 | 作用 |
| --- | --- |
| A：受约束的均匀随机 | 回答是否优于随机 |
| B：历史频次 + 餐次/预算 + 简单近期去重 | 回答是否优于低成本的常识规则 |
| C：长短期画像 + 多样性/探索 + 反馈更新 | 检验完整推荐方案的增益 |

核心指标为明确采纳率、采纳前换选次数、从点击到决定的时间。用户退出或没有再点击不能自动算满意；缺失反馈单独记录。可选轻问“最后吃了它吗”，只在实验中少量采集，区分口头采纳与实际选择。

建议先做 20–30 位自愿用户、跨 1–2 周的探索性试验，按用户/时段随机交替方案并隐藏方案名称。此规模用于检查方向和埋点，不直接声称统计显著；正式样本量按试验方差、用户内相关性和目标提升计算。

建议成功门槛：C 相比 A 的采纳率相对提升 ≥ 15%，且最终确认试验的差异置信区间支持正向增益；相对 B 也要体现值得额外复杂度的收益，或以相近效果显著降低延迟与成本。门槛属建议，需在正式试验前固定。若只比随机好、却不如 B，应优先保留简单方案。

历史数据回放按时间划分训练与测试，禁止用未来订单更新过去画像。命中后来吃的菜只说明预测能力，不能直接证明用户更满意。新用户、少记录用户与老用户分别统计。

## 8. 建议分期与主要风险

| 阶段 | 建议交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 可行性验证 | 一种真实数据导入方案、菜品归一抽检、A/B/C 对照报告 | 数据可持续获得，方案有改善信号 |
| 首版 MVP | 安卓单按钮与换选、可跳过导入、轻量个性化、次级依据查询、数据删除 | 主流程快且简单，能解释失败与缺失数据 |
| 迭代版 | 增量同步、端侧模型对照、更细分的重复/探索策略 | 实测证明值得增加复杂度 |
| 长期探索 | 可靠商家可获得性、更广数据源、进一步端侧化 | 接入权限与收益均已确认 |

数据接口不可用时，退到主动导入与基础候选；画像不准确时允许轻量纠正；地域变化或候选过时时降低历史商家的权重；用户无反馈时保留不确定性，不强行下结论。

## 9. 后续待确定事项

1. 第一批服务哪个地区、哪些外卖平台，是否有可自愿提供的真实订单样本？
2. 最终答案首先是菜品、餐食组合，还是必须包含可下单商家？建议从菜品开始。
3. 首次建档可接受等待多久？允许哪类数据进入云端？建议日常推荐默认本地完成。
4. 最低安卓版本、最低支持机型、单用户预算和试验招募规模。

以上问题影响下一阶段选型，不妨碍当前需求归档；当前采用的都是可修订建议。

## 10. GitHub 同类项目与复用补充

已补充[开源项目调研](GitHub开源项目调研.md)，重点核查 eatwhat、whatToEat、Meal-Planner、eat-what、HowToCook 与 RecBole。存在可借鉴的本地排序、历史反馈、随机选择和菜品内容，无需全部自行摸索；完整外卖记录导入与真人推荐效果仍未被这些候选证明。

建议在第 8 节可行性验证开始时，先评估候选内容与已有规则实现，再决定开发边界。优先参考 eatwhat 的本地推荐链路和 whatToEat 的基础选择；食谱内容可考察 HowToCook。部分仓库存在许可证缺失或说明不一致，已逐项记录，尚未视为已确定可直接引入的依赖。

本次仅补充调查与复用建议，未复制代码、安装项目或修改原始产品目标。
